# Cibim — notes for Claude Code

Personal Android app for tracking every expense and income for one household, called Cibim. It replaces the Money Manager app. The repo, the code and the package name `com.eminallahverdi.balance` stay Balance: the package can't change now that real data and the Google sign-in depend on it. Owner: Emin, a senior Android developer. The repo is **public**: never commit personal data, backups (`*.mmbackup`, `*.db`), real names of family members, or signing keys.

## Where the design lives
- Design system (tokens, type, guidelines): https://claude.ai/artifact/4ifuwdoahAni7s3raTtnZJ. A copy is in `docs/design/` (`tokens.json`, `README.md`).
- Screens (approved for the MVP): https://claude.ai/artifact/SxvUVfe8cVcaBCsfdG8jhW
- Keep the design current: once a UI change is confirmed on a device, add anything the artboards don't show to the screens file, and to the design system if it's a new pattern. Features not built yet stay in the design as they are.
- Compose implementation: `core/designsystem`. `BtTheme.colors` and `BtTheme.type` mirror `docs/design/tokens.json` one to one. When a token changes, update both.
- Picking one thing always opens a bottom sheet (`ChoiceSheet` and `OptionRow`), never a dropdown menu or spinner, even for a short list.

## Stack
Kotlin and Jetpack Compose (Material 3 under our own design system), Hilt, Room, DataStore, Coroutines/Flow, type-safe Navigation Compose, Glance widgets, WorkManager. No backend. Backup goes to the hidden app-data folder in the user's own Google Drive.

Background work must stay cheap on battery:
- No polling, exact alarms, foreground services or wake locks of our own. Prefer events (Room flows, the notification listener) to checking on a timer.
- At most one daily WorkManager job per feature, doing its work and ending in seconds. Reminders accept arriving late under Doze, which is what makes them cheap.
- Drive backup runs once a night at 03:00. It waits for Wi-Fi, or any connection if the user allows mobile data, and doesn't wait for charging: the owner wants it every night, and it takes seconds. With no network at night it runs as soon as there is one.
- Glance keeps a job awake for about 45 s after every widget redraw, so redraw only when something a widget shows has changed.
- A plain daily period slips later by however late each run was. Work tied to a time of day books its next run with `bookDailyWork`, as the evening reminder, payment reminders and the widgets' midnight refresh do.

## Domain rules
- Money is always `Long` minor units. Never use floating point.
- Amounts always show two decimals (₼4.40, ₼3,435.00), even where the design mock-ups show whole numbers. In a tight space the text shrinks; it's never cut off or rounded. The one exception is the small label above the selected chart bar, where 1,000 and up reads 3.4k; the card's heading has the exact figure.
- Every expense has a category (or a sub-category, whose parent is the reporting category) and a **person** ("For whom"). Each category has a default person.
- People and categories are fully user-editable: add, remove, reorder, colour, and photo avatars for people. Removing something that's in use **archives** it instead of deleting it.
- An archived account can be deleted for good, from Accounts. Its page lists everything that uses it, and each row opens to change or delete, as in History. Move all sends entries, recurring payments and what merchants remember to another account in one database transaction: that account takes on its balance, and transfers between the two go, because they'd be from an account to itself. Delete takes them with it, which changes past months and, through transfers, other balances, so the dialog names each one. Neither can be undone, apart from restoring a backup.
- Balances are always today's, so Home shows Total balance and the account chips only on the current month. Past months show Spent and Income.
- The eye (Settings: "Hide balance and income") hides balances, account chips, income, saved, transfers, adjustments and money borrowed or lent. Spending stays visible: the owner finds it less sensitive.
- Transfers move money between accounts and never count as spending or income. `ADJUSTMENT`, `INTERNAL` and `DEBT` carry a signed amount and are left out of charts.
- Bank loan payments are normal spending everywhere. A loan finishes when its payments run out, and logging a payment counts towards it; skipping one doesn't.
- A debt is money between the owner and someone outside the household, so its name is plain text, not a `Person`. With a category it's something they paid for the owner, like a share of lunch: no money moves until it's paid back, and then it's an ordinary expense in that category. Without one it's a plain loan: `DEBT` entries change a balance when it's made and when it's repaid, and are never spending or income. What's left is worked out from a debt's entries, so editing or deleting one keeps it right.
- Nothing adds a transaction by itself: the owner logs every entry so they see what they spent. Automation stops at a ready-made entry they save, as recurring reminders do. The one exception is Auto-confirm known merchants on To confirm: it's off by default, turning it on always asks first, and it only adds merchants the user has confirmed themselves. An entry counts as a reminder's when it has the same name, or the same category and amount, from 10 days before its date (2 for weekly), because billing dates move.
- Bank notifications stay on the device, and only the apps the user picks in Settings are read. For other apps, only the package name is kept, so they can be picked. Nothing depends on a particular bank, and app package names are deliberately not hardcoded, because the app is for anyone. `parseBankNotification` in core:model looks for a sum in manats with a word for money moving. A foreign card payment is read from the manat figure sent with it, which includes commission; a separate commission line, an exchange rate and a balance are never the amount. Login codes and offers are ignored. A plus sign before the sum, or a word for money arriving, makes it income. Taking cash out (Nağdlaşdırma, an ATM and the like) is a `TRANSFER`, whichever shop's machine it came from. A shop's name loses what card statements add: the processor before a star, a billing word after, and a payment reference that changes with every charge, so ANTHROPIC* CLAUDE SUB reads as Claude. A phone number written as one is dropped too, so a top-up to Nar 77:1234567 reads as Nar, while a bare run of digits, like a reference, still keeps its line out of shop names. That bank puts invisible left-to-right marks inside its sums, so a notification can look right and still not read, and a screenshot won't show why: compare against a live one from `adb shell dumpsys notification --noredact`, byte by byte. Invisible format characters are stripped before anything is read. A real payment from it was read on the owner's phone on 2026-11-03, first by Cibim Dev, then by Cibim 1.1.0. Money arriving hasn't been seen, so expect to adjust its wording lists. What's already in the shade is read when the listener connects and when bank notifications are turned on or an app is picked, because the notification that makes an app pickable has already gone by. A notification's fingerprint stops it being added twice, and a skipped entry stays skipped.
- `guessFor` in core:model fills in a pending entry, in order: a merchant the user confirmed, another spelling of a merchant they've used, a recurring payment or loan by name or by its amount within 10 days of its date, then category names and `CATEGORY_HINTS` in the notification's merchant and title. Anything but a confirmed merchant is marked Suggested, and auto-confirm never acts on it. When the real backup is imported, check the hints still point at the owner's categories. Anything personal goes in the on-device mapping file, not the hints, because this repo is public.
- A notification's card decides its account, ahead of every other guess, when an account has that card's last four digits saved (Accounts, edit an account). Those digits are the only card detail kept, and they stay on the device and in its backup. A withdrawal goes from that account to the first cash account, with no merchant, category or person, so it can't count as spending and auto-confirm never acts on it. With no cash account it has no Confirm, and Edit opens quick add as a transfer.
- The evening reminder goes off at the time set in Settings, only if nothing is dated today, and opens quick add. Adding an entry clears it. A run so late it's the next morning stays quiet.
- Every Room schema change needs a migration, because the owner's real data lives in this database. From the import on, treat the data on the phone as real: never wipe it to test something.
- A backup keeps the last 7 in the app-data folder, which only this app can see. A night with no backup shows on Home from about 30 hours after the last one (`isBackupOverdue`), and it taps through to Settings. With backups off, nothing nags: that was the user's choice. Dev and Prod share that one folder, because Drive gives one per Google Cloud project, so each backup is marked with its environment. An app only ever counts and deletes its own, so testing can't push out a real backup. Prod never offers Dev's backups. Dev offers real ones too, marked Real data, to try an update on a copy of them, and restoring only reads. A backup with no mark is from before Dev existed, and counts as Prod's.
- The import is told how to map things by a JSON file on the device (`ImportMapping` documents it), because it names the owner's family. It never goes in this repo, and `*-mapping.json` is gitignored. Test data for the importer uses invented names only. In the old app, tags did three jobs (people, sub-categories, merchants), and the categories named after people really meant "for whom", so both become the For whom field. Entries with no category were balance corrections and import as `ADJUSTMENT`. Taksit income was an offset for paying by card, and the bank loan paid out was not earnings, so both import as `INTERNAL`: the balance stays right and they aren't income.
- The app must work for anyone the owner shares it with. First run shows onboarding: name, people, a category template, and optionally a CSV import or a Drive restore. Nothing is written until the last tap, and then all at once. The backup page signs in to Google there and then, but backups only turn on at the last tap, when the first one goes straight away, so leaving halfway never sends an empty app to Drive. An account that already has backups is offered a restore first, because starting fresh beside them would push them out within a week. `needsOnboarding` decides who sees it: installs from before it have no flag, but every one of them has data, so an install with data is marked done and never asked. A restore skips it the same way.
- The CSV import reads what Export CSV writes, by column name in any order, and any spreadsheet shaped like it: only Date and Amount are needed. It's in onboarding only, because running it again would add every entry twice. Lines it can't read are counted and left out.
- Android's notification permission is asked before Home when a reminder is on, it isn't allowed, and this install hasn't asked (`needsNotificationAsk`). "Asked" lives in InstallPreferences, outside the backup, so a restore on a new phone asks again.

## Commands
```
./gradlew testDebugUnitTest :core:model:test   # unit tests, all modules (core:model is pure JVM, so it has `test`, not `testDebugUnitTest`)
./gradlew :app:assembleDevDebug      # Cibim Dev for everyday work (applicationId com.eminallahverdi.balance.dev)
./gradlew :app:assembleDevRelease    # Cibim Dev shrunk with R8, the way it ships
./gradlew :app:assembleProdRelease   # Cibim, the real app (applicationId com.eminallahverdi.balance)
```
CI (`.github/workflows/android.yml`) runs the tests and a dev debug build on every push, and publishes from main and from tags (see below).

## Environments and releases
Two flavors, side by side on one phone, each with its own name, icon and data: `dev` (Cibim Dev, violet icon) to try changes, and `prod` (Cibim) for the real data. Prod has no debug variant, so the variants are `devDebug`, `devRelease` and `prodRelease`. Only `app` has flavors; other modules learn which app they're in through the injected `AppEnvironment`.

Release flow, with no USB: pushing to main publishes `dev-<commits>` as a GitHub pre-release, the newest 5 kept. Once it holds up on the phone, tagging that commit, like `git tag v1.2.0 <commit>`, then pushing the tag, publishes that same code as Cibim 1.2.0, with its R8 mapping beside the APK to read crash traces. Both land on GitHub Releases. They're public, like the repo, and hold no personal data. Play Protect blocks a first install from a browser, automatically and by design, because the app declares notification access: it does that for apps with sensitive permissions from browsers, messaging apps and file managers. `adb install` isn't covered, so a first install goes over USB. After that, updates from the browser go through: `dev-32` installed over `dev-30` from Chrome on the owner's phone. That only works with the same key, so an app already installed with another key has to be uninstalled and installed over adb. A build Android refuses as older means its version code is lower: `versionCode` counts commits, which is why CI checks out with `fetch-depth: 0`. `versionName` comes from the tag through `-PappVersion`.

Signing: every variant uses one key, read from `keystore.properties` (see `keystore.properties.example`). CI writes that file from the secrets `KEYSTORE_BASE64`, `KEYSTORE_PASSWORD`, `KEY_ALIAS` and `KEY_PASSWORD`. With no key a build falls back to the debug key, so CI and a fresh clone still build, but publishing needs the real one. The owner creates and holds the key: its password never passes through Claude, and it's never committed. Losing it means no build can update the installed apps again: they'd need reinstalling and a Drive restore. A key can't be added to an install signed with another one, so a debug-key build of Prod has to be uninstalled before the real one goes on.

R8 only runs on `*Release`, so anything that works by name or reflection can break there and nowhere else. After a change like that, try `devRelease`. Release builds aren't debuggable, so `run-as` doesn't work on them.

The backup round trip, and moving or deleting an account and the CSV import on a real database, are instrumented tests, which CI doesn't run. Always aim them at the emulator, or they install to the phone too:
```
ANDROID_SERIAL=emulator-5554 ./gradlew :core:backup:connectedDebugAndroidTest :core:data:connectedDebugAndroidTest
```

Drive runs through the owner's Google Cloud project, Cibim: Drive API on, published to production (the `drive.appdata` scope needs no review, but testing mode ends consent after 7 days), and an Android OAuth client for each package name and signing SHA-1, which `./gradlew :app:signingReport` prints. Prod and Dev each have one and share the real key's SHA-1. The "Cibim debug" client is left over from an app that no longer exists, and nothing uses it. The consent screen links to this repo and `docs/privacy.md`, so moving that file means updating Branding. A build with no client says Drive isn't set up.

The AVD `Pixel_3a_API_30` (Android 11) boots with `emulator -avd Pixel_3a_API_30`. `installDevDebug` installs to everything connected, so while the phone is plugged in, install to the emulator alone with `adb -s emulator-5554 install -r app/build/outputs/apk/dev/debug/app-dev-debug.apk`. Test bank notifications with `adb -s emulator-5554 shell "cmd notification post -S bigtext -t 'Bank' tag 'Payment 12.40 AZN, SHOP'"`, which arrive from the app called Shell. Rounded widgets need Android 12, so they're square there.
